This module blocks installing, upgrading and uninstalling modules from
the web interface and from RPC, including for administrators.

Odoo already restricts module operations to administrators. But on a
production database, the customer usually has an administrator account,
and an install from the web interface:

-  runs on the live database, in the web worker that received the click,
   and takes locks on the tables it changes, which can freeze Odoo for
   every user;
-  installs a module that has not been assessed and tested on staging;
-  is not in the code, so staging, a new environment or a restore built
   from the repository will not have it.

The rule is simple: a module operation is refused when it runs **inside
an HTTP request** (web client, ``/json/2``, XML-RPC, JSON-RPC), whoever
the user is, unless the request comes from an allowed IP address.
Outside an HTTP request (``odoo -i/-u``, ``click-odoo-update``,
``odoo shell``, server-side scripts), it goes through. A module added to
the code as a dependency of an upgraded module is still installed at
deploy time.

The guarded entry points are:

-  ``button_install``, ``button_immediate_install``;
-  ``button_upgrade``, ``button_immediate_upgrade``;
-  ``button_uninstall``, ``button_immediate_uninstall``,
   ``button_uninstall_wizard``, ``module_uninstall``;
-  "Apply Scheduled Upgrades" (``base.module.upgrade``).

This covers the Apps menu, the ``module_*`` checkboxes in Settings, and
the buttons of other addons that install modules (localizations
installed when setting a company's country, payment providers, the
website configurator, Point of Sale options, ...). "Update Apps List"
stays allowed: it installs nothing.

Each refused call raises an error telling the user which modules were
not processed, and is logged at ``WARNING`` level with the method, the
modules, the user and the IP address.

Configuration
=============

Both options are read from the server configuration file, never from the
database: an administrator can change system parameters from the web
interface, and that is the user being blocked.

They go in a ``[module_block_install]`` section of their own, not in
``[options]``: since 19.0, Odoo warns about every option of
``[options]`` it does not know.

.. code:: cfg

   [module_block_install]
   enabled = True
   allowed_ips = 203.0.113.10,198.51.100.0/24

With ``server_environment`` installed, the section is read from its
configuration instead.

-  ``enabled``: blocking is on by default as soon as the module is
   installed. Set it to ``False`` on development and test environments.
-  ``allowed_ips`` (optional, empty by default): a comma-separated list
   of IP addresses or networks (CIDR notation). Requests coming from
   these addresses are not blocked, for example to let the integrator
   install a module from the web interface during a planned
   intervention.

Behind a reverse proxy, Odoo only sees the client's real address when
``proxy_mode`` is on and the proxy sends the ``X-Forwarded-*`` headers.
Otherwise every request carries the proxy's address: never allow that
address, it would let everyone through.

The ``/xmlrpc``, ``/xmlrpc/2`` and ``/jsonrpc`` endpoints are only
recognised as HTTP requests once the module's code is loaded in the
server process. A worker loads it with the database's registry, which,
on a server without ``dbfilter`` and without ``--database``, can happen
during the first such call. To close that gap, also load the module
server-wide:

.. code:: cfg

   [options]
   server_wide_modules = base,rpc,web,module_block_install

Usage
=====

Once installed, an administrator who tries to install, upgrade or
uninstall a module from the web interface gets an error such as:

   Module installation is disabled on this database. The following
   modules were not installed: pos_restaurant. Ask your Odoo partner to
   add them to the project and deploy them.

To install a module, add it to the code (for example to the ``depends``
of the project's bundle module) and deploy it with ``odoo -u`` or
``click-odoo-update``.

In Settings, modules are installed when the settings are saved. When the
install is refused, the whole save is rolled back, including the other
settings changed at the same time.

Known issues / Roadmap
======================

-  A direct ``write`` on ``ir.module.module.state`` over RPC is not
   guarded: an administrator could mark a module ``to install``, and it
   would be installed at the next deploy.
-  "Import Module" (``base_import_module``) is not guarded.
-  The ``module_*`` checkboxes in Settings could be made read-only when
   blocking is on, instead of refusing the whole save.
-  Anyone with access to the server (``odoo shell``, ``psql``, the
   command line) is not blocked, on purpose: that is how deployments
   work.
